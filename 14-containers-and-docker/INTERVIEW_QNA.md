# Interview questions — Containers and Docker

Each answer is what an interviewer hopes to hear: the mechanism, the trade-off, and the production gotcha. The numbers quoted come from this module's demos.

---

## 1. How is a container different from a virtual machine?

A virtual machine emulates hardware and runs its own full operating system kernel on top of a hypervisor. It's strongly isolated, takes gigabytes, and boots in tens of seconds. A container is an ordinary process on the host's kernel that the kernel *isolates*: namespaces give it its own view of the filesystem, process IDs, network, and hostname, and cgroups limit its CPU and memory. There's no second kernel, so a container starts in well under a second (topic 01's starts, runs, and exits in under one) and images are megabytes to hundreds of megabytes. The cost is weaker isolation, since everything shares one kernel, and containers can only run programs built for that kernel's OS. That's why Docker Desktop on macOS and Windows quietly runs a small Linux VM: every container in topic 01 reports a `linuxkit` kernel, not Darwin. The practical win is reproducibility: the image pins the Java runtime and OS libraries, so "works on my machine" becomes "works in this image", everywhere.

## 2. What's the difference between an image and a container, and where do a container's file changes go?

An image is a read-only stack of layers, roughly one per file-changing Dockerfile instruction. Layers are content-addressed, so images that share a base store those layers once, and a pull fetches only the layers you don't already have. A container is a running process started from an image, plus one thin writable layer on top. Every file it creates or modifies goes into that layer (`docker diff` lists them), and the image is never modified. Consequences: two containers from one image don't see each other's changes; removing a container deletes its changes; and anything that must survive (database files, uploads) belongs in a volume. It also explains the build cache: Docker reuses a layer while the instruction and its inputs are unchanged, and the first changed step plus every step after it re-runs, so put the slow, rarely changing steps first.

## 3. What is a multi-stage Docker build, and why use one for a Spring Boot app?

A Dockerfile with several `FROM` lines. Each starts a stage, and only the last stage becomes the image. For Spring Boot, stage one uses a Maven + JDK image to compile and package the jar; stage two starts from a JRE-only image and copies just `app.jar` from stage one with `COPY --from=build`. The build tools, source code, and downloaded dependencies never reach the final image. That gives a smaller image (topic 03: 516 MB against 982 MB), less attack surface (no compiler or Maven, and fewer packages to patch), no source code in the artifact, and a build that needs nothing but Docker. Pair it with good layer ordering (`pom.xml` before `src/`) and a BuildKit cache mount for `~/.m2`, so a one-line change doesn't re-download every dependency (16 s against 3 s in the demo). Follow-ups worth raising: use the exec-form `ENTRYPOINT` so the JVM receives stop signals; set `-XX:MaxRAMPercentage`, because the default heap is 25% of the container's memory limit; and go further with layered jars (topic 04), so a code change ships about 80 kB instead of the whole 21 MB jar.

## 4. How should a Spring Boot container get its configuration and secrets, and why not bake them into the image?

The image should be identical in every environment. What you tested in staging is what runs in production, and only configuration differs. Anything built into an image is readable by anyone who can pull it: `ENV` values appear in `docker image inspect`, build `ARG`s used by a `RUN` appear in `docker history`, and a file copied in then `rm`-ed still sits in its original layer, because layers are read-only and an `rm` only adds a hiding layer. So supply configuration at start-up. Non-secret, per-environment settings go in environment variables, which Spring maps with relaxed binding (`SPRING_PROFILES_ACTIVE`, `APP_GREETING` → `app.greeting`, `SPRING_DATASOURCE_URL`), set via `-e`, `--env-file`, Compose `environment:`, or a Kubernetes ConfigMap. Secrets are better mounted as files and read with `spring.config.import=configtree:/run/secrets/`, where each file name is a property name. Env vars are visible to anyone who can `docker inspect` the container, inherited by child processes, and often end up in logs; mounted files aren't shown by `inspect`. That file layout is exactly what Compose secrets and Kubernetes Secrets produce. Build-time secrets use BuildKit's `RUN --mount=type=secret`, which never writes them into a layer.

## 5. A Spring Boot container is running and healthy, but you can't reach it. Walk through the causes.

Work from the outside in. Was the port published? Without `-p host:container` (or Compose `ports:`), nothing on the host forwards to the container, and `EXPOSE` doesn't publish anything. Is the app listening on the container's network interface? With `server.address=127.0.0.1` it answers `curl` inside the container but published traffic gets "connection reset"; it must listen on `0.0.0.0`, Spring Boot's default. Is the host port free? A second container on the same host port fails with "port is already allocated". For container-to-container calls: `localhost` is the calling container itself; names resolve only on user-defined networks (and in Compose), not on the default bridge; and the URL uses the target's *container* port (`http://inventory:8080`), not the published one. The target doesn't need `-p` at all for other containers to reach it.

## 6. What happens, step by step, when you `docker stop` a Spring Boot container, and how do you make sure no request is dropped?

`docker stop` sends SIGTERM to the container's PID 1, waits for the stop timeout (`docker stop -t`, Compose `stop_grace_period`, Kubernetes `terminationGracePeriodSeconds`), then sends SIGKILL, which can't be caught. Exit code 143 means the process exited on SIGTERM; 137 means it was SIGKILLed. For no dropped requests, three things must line up. First, Java must be PID 1 so it receives SIGTERM: use the exec-form `ENTRYPOINT ["java","-jar","app.jar"]`. In shell form `/bin/sh` is PID 1 and doesn't forward the signal, so the app is always killed at the timeout (topic 09: 10.2 s, exit 137). Second, Spring Boot must shut down gracefully: since 3.4, `server.shutdown=graceful` is the default, so the server stops accepting new requests and waits for in-flight ones, up to `spring.lifecycle.timeout-per-shutdown-phase` (default 30 s); `immediate` drops them. Third, the Spring timeout must be shorter than the platform's grace period, or the platform kills the app mid-wait. In Kubernetes there's a fourth: traffic must stop arriving before the pod stops, which readiness and a short pre-stop delay handle. Background work (`@Async`, schedulers, message consumers) has its own shutdown behaviour and should be idempotent, because a kill can always happen.

## 7. Why test against a real database with Testcontainers when H2 is faster? How does it work with Spring Boot?

H2 is a different database engine. It accepts SQL PostgreSQL rejects (`IFNULL`, `DATEADD`, `SELECT TOP n`), rejects SQL PostgreSQL accepts (`INSERT ... ON CONFLICT`), and has different type rules and locking. A repository test on H2 can pass while the same query fails in production, and H2's `MODE=PostgreSQL` doesn't close the gap, because it's still H2 with H2's functions (topic 11). Flyway migrations written for PostgreSQL may not run on H2 at all. Testcontainers starts the real engine (`postgres:17`) in Docker from inside the test, on a random port, and waits until it accepts connections. `@ServiceConnection` (Spring Boot 3.1+) configures the `DataSource` from the container, so there's no URL to manage. With Boot 3.5, `@DataJpaTest`'s default `Replace.NON_TEST` keeps a database the test provides this way, so `replace = NONE` isn't needed for it. It still is when the URL comes from ordinary properties, which would otherwise be silently swapped for H2. Gotchas: non-embedded databases get `ddl-auto: none` by default, so run Flyway or set it; share one container across test classes to keep suites fast; pin the image to production's major version. The cost is Docker on every machine and CI agent, plus a few seconds of startup, so use it for persistence and integration tests and keep plain unit tests for business logic.

## 8. Explain Deployment, Service, liveness and readiness in Kubernetes. How does traffic find a pod?

A Deployment keeps N replicas of a pod template running: it creates pods, replaces dead ones, and rolls out new versions. Pods are disposable and get new IPs, so callers use a Service: a stable DNS name and virtual IP that forwards to pods whose labels match its `selector` and which are currently ready. The link is labels only, so a selector typo or a `targetPort` that doesn't match `containerPort` is accepted by Kubernetes and silently leaves the Service with no endpoints. Readiness answers "can this pod take traffic now?": failing removes it from the Service without restarting it, which is right for warm-up or a temporarily unreachable dependency, and it gates rolling updates. Liveness answers "is this process stuck?": failing restarts the container, so it must check only the app itself. Putting the database in liveness turns a database blip into a fleet-wide restart. Spring Boot exposes `/actuator/health/liveness` and `/readiness`, enabled automatically on Kubernetes. Settings arrive through ConfigMaps (non-secret) and Secrets (base64-encoded, not encrypted, but separately access-controlled and kept out of Git and images), as environment variables or mounted files. Set memory limits deliberately: the JVM sizes its heap from the container limit, and exceeding the limit gets the container OOMKilled.
